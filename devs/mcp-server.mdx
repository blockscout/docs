The Model Context Protocol (MCP) is an open protocol designed to allow AI agents, IDEs, and automation tools to consume, query, and analyze structured data through context-aware APIs.

This server wraps Blockscout APIs and exposes blockchain data like balances, tokens, NFTs, contract metadata via MCP so that AI agents and tools (like Claude, Cursor, or IDEs) can access and analyze it contextually. Connect it to Claude, Claude Code, Codex, or Cursor and query chains in plain English, with answers that come straight from live Blockscout data.

<Tip>
  A single connection reaches every supported chain. Name the network in your prompt and the agent resolves its chain ID, or call `get_chains_list` to browse them all.
</Tip>

## Key Features

- Contextual blockchain data access for AI tools
- Multi-chain support across 100+ hosted EVM chains through the Blockscout API gateway
- Custom instructions for MCP host to use the server
- Intelligent context optimization to conserve LLM tokens while preserving data accessibility, including smart response slicing, opaque cursor pagination, and automatic truncation of large data fields with clear indicators
- Supports MCP progress notifications for multi-step tool operations, allowing clients to track execution status
- Enhanced User Experience: Provides periodic progress updates for long-running API queries (e.g., fetching extensive transaction histories) when requested by the client, improving responsiveness

## Use Cases

- Enabling AI agents to analyze blockchain transactions and account balances.
- Automating blockchain data analysis workflows with context-aware APIs.
- Allowing IDEs to fetch contract ABIs and other relevant smart contract information.

## Connection details

The server uses the Streamable HTTP transport. With your own Blockscout API key you get full rate limits, the complete tool set, and the full set of chains. Without one, the server falls back to a shared gateway key with stricter rate limits and restricted access to some chains and datasets.

|  | With your API key | Without a key |
| --- | --- | --- |
| **URL** | `https://mcp.blockscout.com/mcp` | `https://mcp.blockscout.com/mcp` |
| **Authentication** | `Blockscout-MCP-Pro-Api-Key: <your API key>` header | None |
| **Access** | Full rate limits, full tool set, 100+ chains | Shared key, stricter limits, restricted chains and datasets |
| **Usage** | Counts toward your [Blockscout API plan](https://dev.blockscout.com) | Shared across all keyless users |

<Warning>
  Only paste your API key into the official server at `https://mcp.blockscout.com/mcp`.
</Warning>

<Note>
  Some clients can only send header names from a fixed list, such as Claude custom connectors. For those, send the key in an `x-api-key` header instead. If both headers are present, `Blockscout-MCP-Pro-Api-Key` wins.
</Note>

## Tools

The server exposes 16 tools. Your agent chooses which tool to call, so prompts don't need to name them. The same tools are also available as versioned REST endpoints under `/v1/...`.

| Category | Tool | Returns |
| --- | --- | --- |
| Session | `__unlock_blockchain_analysis__` | Server reference data, the `blockscout-analysis` skill pointer, and the URI resolution rule. Called once per session, before any other tool. |
| Chains | `get_chains_list` | Supported chains, filterable by name, chain ID, native currency, or ecosystem |
| Addresses | `get_address_info` | Comprehensive information about an address |
|  | `get_address_by_ens_name` | The address for an ENS name |
| Balances | `get_tokens_by_address` | ERC-20 token holdings for an address |
|  | `nft_tokens_by_address` | NFTs owned by an address |
| Transactions | `get_transactions_by_address` | Transactions for an address |
|  | `get_transaction_info` | Comprehensive details for a transaction |
| Transfers | `get_token_transfers_by_address` | ERC-20 token transfers for an address |
| Tokens | `lookup_token_by_symbol` | Tokens matching a symbol |
| Blocks | `get_block_info` | Detailed block information |
|  | `get_block_number` | The block number and timestamp for a date and time, or the latest block |
| Contracts | `get_contract_abi` | ABI for a smart contract |
|  | `inspect_contract_code` | Source code or metadata for a verified contract |
|  | `read_contract` | The result of a read-only contract function call |
| Advanced | `direct_api_call` | The response from a curated raw Blockscout API endpoint |

## Good to know

- **Read-only.** The server only reads on-chain data. It cannot sign or broadcast transactions.
- **Tool calls use your API credits.** The server reads data through the Blockscout API, so calls made with your key are metered against your plan. When your balance runs low, tool responses can include an advisory note. If credits run out, calls fail with a payment-required error (HTTP 402 on the REST endpoints).
- **Without a key, limits are tighter.** The shared gateway key has stricter rate limits and may restrict access to certain chains or datasets. For full access, add your own free key.
- **Responses are trimmed for agents.** Large results are sliced with opaque pagination cursors, and long data fields are truncated with clear indicators, so agents keep context without losing access to the data.
- **Keep tool approvals on.** Data returned by any MCP server can contain untrusted text, so leave your client's approval prompts enabled, especially when other MCP servers share the session.

## Architecture and Data Flow

Every data request is validated against the supported chain list, then sent to the authenticated Blockscout API gateway with your key.

```mermaid
sequenceDiagram
    participant AI as MCP Host
    participant MCP as MCP Server
    participant BENS as ENS Service
    participant CS as Chainscout
    participant Config as Blockscout API Config
    participant BS as Blockscout API

    AI->>MCP: __unlock_blockchain_analysis__
    MCP-->>AI: Reference data + skill pointer

    AI->>MCP: get_address_by_ens_name
    MCP->>BENS: Forward ENS name resolution request
    BENS-->>MCP: Address response
    MCP-->>AI: Formatted address

    AI->>MCP: get_chains_list
    par Fetch chain sources
        MCP->>Config: GET /api/json/config (supported chains + URLs)
        Config-->>MCP: Chain ID → URL mapping
    and
        MCP->>CS: GET /api/chains (chain metadata)
        CS-->>MCP: Chain registry
    end
    MCP->>MCP: Join: API chains + Chainscout metadata
    MCP->>MCP: Cache chain data
    MCP-->>AI: Formatted chains list

    Note over AI: Host selects chain_id as per the user's initial prompt

    AI->>MCP: Tool request with chain_id
    MCP->>MCP: Validate chain via cached API config
    par Concurrent API Calls (when applicable)
        MCP->>BS: Request to Blockscout API (for Basic Info)
        BS-->>MCP: Primary data response
    and
        MCP->>BS: Request to Blockscout API (for First Transaction of Account)
        BS-->>MCP: First transaction response
    and
        MCP->>BS: Request to Metadata endpoint through the API (for enriched data)
        BS-->>MCP: Metadata response
    end
    MCP-->>AI: Formatted & combined information
```

How a session flows:

1. **Unlock.** The agent calls `__unlock_blockchain_analysis__` once to receive server reference data and a pointer to the `blockscout-analysis` skill.
2. **Chain selection.** `get_chains_list` joins the chains supported by the Blockscout API with chain metadata (name, ecosystem, testnet flag, native currency) from Chainscout. Only chains present in both sources are listed. The result is cached.
3. **Data requests.** Each tool call is validated against the cached chain configuration, then sent to the Blockscout API. Independent requests run concurrently. For example, `get_address_info` makes three at once: basic on-chain data, the first transaction, and address metadata. A failure in a secondary request is reported in the response `notes` instead of failing the whole call.
4. **Key handling.** Your API key is sent only to the Blockscout API. ENS resolution and Chainscout never receive it, and chain discovery works without a key.

### REST API data flow

The same tools are also available as REST endpoints under `/v1/`. These are thin wrappers that call the same tool functions as the MCP server.

```mermaid
sequenceDiagram
    participant REST as REST Client
    participant MCP as MCP Server
    participant CS as Chainscout
    participant Config as Blockscout API Config
    participant BS as Blockscout API

    Note over REST, MCP: Static Endpoints
    REST->>MCP: GET /
    MCP-->>REST: HTML Landing Page

    REST->>MCP: GET /health
    MCP-->>REST: {"status": "ok"}

    Note over REST, MCP: REST API Endpoint (calls same tool function as MCP)
    REST->>MCP: GET /v1/get_block_number?chain_id=1
    Note over MCP: REST wrapper calls get_block_number() tool function
    MCP->>MCP: Resolve chain_id via cached API config mapping
    MCP->>BS: GET /api/v2/blocks/latest
    BS-->>MCP: Block data response
    MCP-->>REST: JSON Response (ToolResponse format)
```

The MCP server gives your agent the tools. The `blockscout-analysis` skill teaches it to use them well: how to page results, handle rate limits, fall back to the REST API, and script ad-hoc analysis. The `web3-dev` skill teaches it to build apps, bots, and indexers directly on the Blockscout API.

Install both from the [agent-skills repository](https://github.com/blockscout/agent-skills), or see the [AI agents page](https://dev.blockscout.com/agents) for per-agent install commands.
